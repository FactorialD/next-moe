# Память для полного обучения десяти профилей

Расчёт от 12 октября 2026 для [архитектуры v0.3](architecture.md) и точных параметров [семейства](../configs/model-family.json). Это аналитическая нижняя граница хранения состояний с явно неизвестной добавкой для активаций и временных буферов, а не измерение peak VRAM. Обучаются все neural и Engram параметры; исходные top-k не меняются.

## Два сравниваемых режима

Базовый режим без дополнительных оптимизаций памяти: BF16 веса и градиенты, FP32 master weights и два FP32 Adam moment tensors. Это 2 + 2 + 4 + 4 + 4 = **16 bytes/parameter**. BF16 уже является выбором mixed precision; колонка не означает буквально FP32 обучение без любых оптимизаций.

Режим с оптимизациями: BF16 веса и градиенты, FP32 master weights, два 8-bit Adam moment tensors: 2 + 2 + 4 + 1 + 1 = **10 bytes/parameter**. Предполагается реализация, поддерживающая такое сочетание для всех обучаемых tensors, включая Engram. Scales, small tensors в FP32, padding и optimizer workspace увеличат результат. Квантизация состояний оптимизатора требует проверки устойчивости и качества обучения. Для уменьшения активаций предусматривается выборочный checkpointing/recomputation блоков. FlashAttention и эффективные fused/chunked kernels GDN/MoE/LM loss рекомендованы в обоих режимах.

Показано суммарное хранение одной копии training states на GPU, **без CPU offload и без сокращения числа обучаемых параметров**. На одном GPU это нижняя граница его VRAM; при распределении — объём глобальных состояний, который надо разместить между устройствами. DDP реплицирует состояния, FSDP/ZeRO-3 их шардирует; дополнительная память зависит от topology и степени шардирования.

| Neural + Engram, B | Без дополнительных оптимизаций, GiB | С оптимизациями, GiB |
| --- | ---: | ---: |
| 0.2 + 0.1 | 4.38 + A₀ + W₀ | 2.74 + A₁ + W₁ |
| 0.5 + 0.2 | 10.74 + A₀ + W₀ | 6.71 + A₁ + W₁ |
| 1 + 0.4 | 21.17 + A₀ + W₀ | 13.23 + A₁ + W₁ |
| 3 + 1 | 61.63 + A₀ + W₀ | 38.52 + A₁ + W₁ |
| 7 + 2 | 133.46 + A₀ + W₀ | 83.41 + A₁ + W₁ |
| 20 + 5 | 375.18 + A₀ + W₀ | 234.49 + A₁ + W₁ |
| 70 + 20 | 1,314.03 + A₀ + W₀ | 821.27 + A₁ + W₁ |
| 125 + 50 | 2,592.62 + A₀ + W₀ | 1,620.39 + A₁ + W₁ |
| 400 + 100 | 7,392.84 + A₀ + W₀ | 4,620.52 + A₁ + W₁ |
| 1000 + 200 | 17,820.85 + A₀ + W₀ | 11,138.03 + A₁ + W₁ |

A₀/A₁ — peak live training activations; W₀/W₁ — буферы kernels, dispatch/all-gather, optimizer updates, quantization metadata и allocator. Это не одинаковые постоянные для всех моделей. Они ещё не измерены и не включены в числовую часть таблицы. Нельзя гарантировать, что оптимизированный peak всего процесса всегда ниже: реализация recomputation и communication может менять временные пики.

Для будущего измерения стартовый сценарий: 32 768 токенов, микробатч одна последовательность на replica; затем 128K и 256K. Global batch можно увеличивать gradient accumulation без сохранения активаций всех микробатчей одновременно. Числовая часть таблицы не зависит от длины контекста; неизвестная добавка зависит.

Не добавлять к таблице inference KV cache как отдельную training cache: при обычном full-sequence teacher-forced training persistent autoregressive cache выключен, нужные для backward K/V учитываются в активациях. Малое fixed decode state GDN также не является оценкой GDN backward memory. В наивном attention сохранённые score/probability matrices могут расти квадратично с контекстом; FlashAttention их не материализует целиком. GR имеет четыре потока, а routed FFN активации зависят от top-k, f, dispatch capacity и checkpoint границ. Поэтому произвольная надбавка 10–20% не заменяет расчёт или измерение.

Например, у 20+5 только состояния занимают 375.18 GiB в базовом режиме или примерно 234.49 GiB с 8-bit moments. При идеальном ZeRO-3 на восьми GPU вклад состояний составляет 46.90 или 29.31 GiB/GPU соответственно; **это не требуемая ёмкость GPU**: к ней добавляются локальные активации и buffers, а временный all-gather требует дополнительного места. Число GPU не выбрано как аппаратное требование.

MoE снижает compute активных экспертов, но не устраняет остальные веса и training states. Sparse Engram lookup не означает, что full Adam states существуют только для строк текущего микробатча. CPU offload или отдельный lazy sparse optimizer являются дополнительными вариантами с иной стоимостью RAM, передачи и семантикой обновления; в двух колонках они не предполагаются.

## Влияние на скорость обучения

Рекомендация: использовать FlashAttention и эффективные kernels в обоих режимах, а checkpointing включать выборочно при нехватке VRAM. Вторая колонка отличается прежде всего форматом состояний Adam и объёмом пересчёта активаций. Числовые границы хранения 16/10 bytes per parameter от этой рекомендации не меняются.

| Оптимизация | Ожидаемый эффект на скорость |
| --- | --- |
| 8-bit Adam moments | Меньше передачи данных при обновлении параметров, но добавляются quantization/dequantization и служебные операции. Может ускорить или замедлить optimizer step; уменьшение storage на 37.5% не означает такой же прирост throughput всей тренировки. |
| Checkpointing блоков | Часть forward выполняется повторно во время backward. Обмен памяти на дополнительные вычисления; цена зависит от выбранных границ и количества пересчитываемых блоков. |
| FlashAttention | Уменьшает материализацию attention intermediates и часто ускоряет attention, особенно на длинном контексте. Итоговый выигрыш модели зависит от остальных компонентов. |
| Fused/chunked GDN, MoE и LM loss kernels | Могут уменьшить memory traffic и kernel overhead. Конкретные kernels и chunk sizes надо сравнивать измерением. |

При одинаковых эффективных kernels в обоих режимах предварительный ориентир для штрафа checkpointing — **примерно 10–30% меньше токенов/с**, в зависимости от объёма пересчёта. Это инженерная оценка для планирования, не benchmark нашей архитектуры и не универсальная граница.

В упрощённой compute-bound модели backward стоит примерно два forward: обычный шаг имеет стоимость F + 2F = 3F, полный пересчёт блоков добавляет примерно F. Тогда шаг занимает около 4F вместо 3F: **на 33% больше вычислений и на 25% меньше токенов/с**. Реальные GDN kernels, GR, dispatch, optimizer updates, communication и дополнительные all-gathers при distributed checkpointing могут изменить это отношение.

Если исходный вариант использует наивный attention с материализацией score matrices, а второй FlashAttention, на 32K–256K второй может оказаться быстрее либо первым помещающимся в память. Это отдельное сравнение реализации attention, а не чистая цена checkpointing. Если экономия VRAM позволяет увеличить полезный микробатч, throughput также может улучшиться; сравнение скорости тогда нужно сопровождать размерами batch и context.

Для измерения сравнивать steady-state tokens/s и peak allocated/reserved VRAM после прогрева и lazy allocation optimizer states. Фиксировать GPU, topology, context, microbatch, global batch, dtype, top-k, kernels и distributed layout; отдельно менять 8-bit moments и checkpointing, чтобы различить их эффекты. CPU offload не входит в эти оценки, а ZeRO/FSDP могут добавлять стоимость коммуникации.

Точные peak VRAM и throughput появятся после реализации kernels, distributed layout и профилирования forward/backward/optimizer steps. Для будущего конструктора следует показывать отдельно training states, activation model, transient buffers, степень шардирования и confidence оценки.
